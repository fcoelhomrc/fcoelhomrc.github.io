Building a test set from your own papers

Part 1 of 3. A step-by-step guide to generating retrieval test questions from your own documents with Ragas, where every question knows which chunks answer it.

August 28, 2026

Evaluating a RAG system, end to end

  1. Building a test set from your own papers
  2. Scoring retrieval without calling a model
  3. Checking the LLM judge before trusting it

This guide builds a test set of 100 questions for a search system over research papers. Each question comes with the ids of the text chunks that answer it. With those ids, you can score any retrieval setup in seconds, with no model calls.

Parts 2 and 3 use this set to compare retrievers and to check an LLM judge. All code is in the Scientific Paper Semantic Search repository.

What we are testing

RAG (retrieval-augmented generation) answers a question in two stages. First a retriever finds the passages most likely to hold the answer. Then a language model writes an answer from those passages.

Before retrieval, each paper is split into chunks of 256 tokens, roughly 200 words. The retriever ranks chunks, not whole papers. If the right chunk is missing from its top results, the language model cannot answer well, so retrieval is the first thing to measure.

Step 1: Decide what a test case looks like

A test case is a question plus the ids of the chunks that answer it. Here is one from the final set:

{
  "question": "How is the WebArena environment delivered and reset?",
  "reference": "The WebArena environment is delivered as dockers, and scripts are provided to reset the environment to a deterministic initial state.",
  "reference_chunk_ids": [12543]
}

To score a retriever on this question, run it and check where chunk 12543 lands in its ranking. That comparison is exact and free. Part 2 turns it into metrics.

The reference field is a gold answer. Retrieval scoring ignores it, but the LLM judge in part 3 uses it.

Step 2: Build a corpus where retrieval is hard

Retrieval is easy when every paper is about something different. Keyword overlap alone then finds the right paper, every setup scores near perfect, and the test tells you nothing.

So the corpus has five topics that share vocabulary: retrieval and RAG, agents, LLM evaluation, efficient inference, and alignment. Each topic has 20 papers, picked by hand from 213 candidates. Papers on the same topic act as distractors for each other.

The result is 100 papers and 11,381 chunks, about 114 chunks for every question. All papers come from arXiv, because other PDF hosts often refuse scripted downloads.

Step 3: Generate questions with Ragas

Writing 100 good questions by hand takes days. Ragas generates them from your own documents in three steps.

  1. An LLM reads each chunk and extracts a summary, its themes and the named entities it mentions.
  2. Ragas links chunks into a knowledge graph. Two chunks get an edge when their summaries are similar or they mention the same entity.
  3. Question writers walk the graph. Each picks one chunk, or a few linked chunks, and writes a question and a gold answer from them.

There are three kinds of question writer. Real examples from the set:

Question type Built from Example
Single-hop One chunk “What is the overall score of ToolAlpaca-13B on simulated tools?”
Multi-hop specific Chunks that share an entity “How does WebArena curate intents and emulate websites for its environment?”
Multi-hop abstract Chunks with a shared theme “How does FLARE address contextual relevance failure points in RAG retrieval?”

Questions are written from a sample of 80 chunks per topic, called the seed pool. The search index still holds all 11,381 chunks, so each question has thousands of possible wrong answers. GLM 5.3 Flash wrote the questions, and the first run cost $0.354 in model calls.

Step 4: Keep the link from question to chunk

Ragas returns each question with the passages it was written from, as text. To get chunk ids, the text has to match a chunk exactly.

By default Ragas re-splits long documents before building the graph, so its passages stop matching your chunks. The fix is to give Ragas your chunks, one document each, and pass an explicit list of steps with no splitter.

After that, every passage Ragas returns is identical to one chunk in the database. A dictionary from chunk text to chunk id gives the gold ids. All 155 generated questions resolved, with one to three gold chunks each.

Step 5: Check the balance

Generated questions can pile up on one topic even when the seed pool is balanced. Count them before you use them.

The first set drew exactly 80 seed chunks from every topic. After review, 58 of its 100 questions were about agents and only 8 about alignment. Ragas favours chunks with many links in the graph, and the agents papers had the most.

With that skew, an overall score would mostly measure one topic. The fix was to run generation once per topic, 31 questions each, and keep exactly 20 per topic.

Step 6: Review every question

Generated questions need a review before use. I had Claude Opus score each of the 155 questions from 0 to 100 for usefulness, one question per call, with a reason and flags.

The review dropped 34 questions. A quota of 20 per topic, filled by score, then cut 21 more, leaving 100. Every verdict appears on a review page where I can override it by hand.

Two of these are easy to miss in any generated set:

  • Gives away its answer’s keyword. A question like “What MiniLM variant does X use?” contains the answer’s key word. Keyword search finds it every time, so the question cannot tell two retrievers apart.
  • Refers to “these” without naming them. Multi-hop abstract questions often ask about “these approaches”, which only makes sense to someone who has already read the source chunk.

The review also edited 18 of the kept questions, several to fix wrong gold answers. When you edit a question, edit its gold answer too, or the judge in part 3 grades against a stale one.

Check the review prompt itself as well. Docling stores tables as row, column = value lines, and the first prompt flagged 80% of table questions as OCR garbage. After one paragraph explaining that format, the keep rate for table questions went from 20% to 82%.

Watch for silent failures

Ragas often fails without raising an error, and you get a test set that looks fine. These five came up here:

What happened What you see Fix
Papers quote the end-of-text token Every extractor call on those chunks fails Treat special tokens as plain text
Similarity threshold too low (0.5) 94.7% of chunk pairs get an edge and question writing hangs Choose the threshold per topic, aiming at about 120 edges
One entity extraction fails No multi-hop specific questions at all Drop incomplete chunks before linking
The generator model reasons by default Empty answers once reasoning uses all 8,192 output tokens Set reasoning effort to low
Multi-hop passages carry a <1-hop> prefix Their gold ids are missing Count unmatched passages after every run

Ragas also drops a question type silently when the graph has no links for it. Check how many questions of each type came out before using the set.

What this set cannot tell you

  • The questions reuse the words of the chunks they came from. That favours keyword search, as part 2 shows.
  • A different chunk may answer a question just as well as its gold chunk. Scores based on gold ids are therefore a lower bound.
  • One model reviewed the questions, and no second reviewer checked it.

Part 2 uses these 100 questions to score five retrievers without a single model call.
