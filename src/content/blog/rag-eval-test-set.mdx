I built 100 test questions over 100 machine learning papers, and each question records the ids of the chunks it was written from. Scoring retrieval then needs no model: compare the retrieved ids with the gold ids. Parts 2 and 3 use this set.

The code is in the [Scientific Paper Semantic Search repository](https://github.com/fcoelhomrc/papers-please), checked at commit `361ff06` (12 Sep 2026).

## The system

Scientific Paper Semantic Search downloads papers, splits them into 256-token chunks and searches them with BM25 and dense vectors. A chat agent answers questions from the search results.

<Diagram src="blog/rag-eval/system.svg" alt="Ingest workers fetch arXiv PDFs, run OCR and embed chunks into Postgres and Pinecone. The query path sends questions from the web app to a LangGraph agent, which searches both stores and sends traces to Phoenix." />

## Five neighbouring topics make retrieval hard

The corpus is five topics of 20 papers each, chosen to share vocabulary: retrieval and RAG, agents, LLM evaluation, efficient inference, and alignment. Papers from unrelated fields would be told apart by keyword overlap alone.

I picked the 100 papers by hand from 213 candidates. The corpus has 11,381 chunks, about 114 per question ([#47](https://github.com/fcoelhomrc/papers-please/issues/47)).

All papers come from arXiv. Semantic Scholar's PDF links often go through doi.org, which returns 403 to a script. Building the link from the arXiv id downloaded all 100 papers ([#41](https://github.com/fcoelhomrc/papers-please/issues/41), [#43](https://github.com/fcoelhomrc/papers-please/issues/43)).

## Ragas wrote the questions from a graph of the chunks

[Ragas](https://docs.ragas.io) builds a knowledge graph and writes questions by walking it. An LLM extracts a summary, themes and entities from each chunk. Edges link chunks with similar summaries or shared entities.

<Diagram src="blog/rag-eval/testset.svg" alt="The corpus feeds a sample of 80 seed chunks per topic into one knowledge graph per topic. Three Ragas question types write 155 questions. Each gold passage is looked up to get its chunk id, then review keeps 100." />

Ragas gets the chunks themselves, one document each, with an explicit list of transforms and no splitter. Its default transforms re-split documents over 500 tokens, and a re-split node no longer matches a chunk.

Every gold passage Ragas returns is therefore byte-identical to a row in the chunks table. A dictionary lookup gives its chunk id, and all 155 questions resolved. Questions come from 80 seed chunks per topic, while all 11,381 chunks stay in the index as distractors.

GLM 5.3 Flash wrote the questions. The first run cost $0.354 in model calls, $0.28 of it for the graph; I did not record the cost of the second.

## Five failures surfaced only by running it

None of the five stopped the run at the point of failure ([#44](https://github.com/fcoelhomrc/papers-please/issues/44)).

| Problem | Effect | Fix |
|---|---|---|
| Papers quote the end-of-text token | tiktoken raised inside every extractor call | Encode special tokens as plain text |
| Similarity threshold 0.5 | 94.7% of 79,401 chunk pairs got an edge, and cluster search hung for 13 minutes | Pick the threshold per topic for about 120 edges |
| 1 of 1,197 entity calls hit its token limit | The relationship builder raised and left zero entity edges, so no multi-hop specific questions | Drop incomplete nodes before building edges |
| GLM 5.3 Flash reasons by default | It spent all 8,192 output tokens reasoning and returned nothing | Set reasoning effort to low |
| Multi-hop passages start with `<1-hop>` | 8 of 11 missed the exact lookup on a trial | A counter of unmapped passages caught it |

Ragas also skips a question type without an error when the graph has no clusters for it. The generator now checks cluster counts before it writes anything.

## Balanced seeds gave unbalanced questions

The first set drew 80 seed chunks from each topic, yet after review 58 of its 100 questions were about agents and 8 about alignment. Ragas picks seeds by their place in the graph, and the agents papers dominated it ([0e8490c](https://github.com/fcoelhomrc/papers-please/commit/0e8490c)).

## Review cut 155 questions to 100

A review pass dropped 34 questions, and a quota of 20 per topic cut 21 more ([6513c33](https://github.com/fcoelhomrc/papers-please/commit/6513c33)). Claude Opus scored each question from 0 to 100 in a separate call, and the quota kept the highest scores. Any verdict can be overridden by hand on the same review page.

A question that names its own answer, such as one asking which MiniLM variant a paper used, is found by BM25 on that name alone. Every configuration then scores the same on it. Multi-hop abstract questions often ask about "these approaches" without saying which.

Review edited 18 of the kept questions, several to fix wrong gold answers from Ragas. An edited question needs its gold answer edited too, or every metric grades against a stale answer.

The review prompt caused one wrong result of its own. It dropped 80% of questions seeded from tables as OCR artifacts, because Docling writes a table as `row, column = value` triplets. A paragraph in the prompt describing that format raised the keep rate for table questions from 20% to 82%.

Of the kept questions, 46 have one gold chunk, 45 have two and 9 have three.

## Limits

- The questions are synthetic and reuse the words of their chunks, which favours BM25. Part 2 shows the effect.
- Each question's gold chunks are the passages it came from. Another chunk may answer it as well, so label-based scores are a lower bound.
- One model reviewed the questions, and no second reviewer checked its verdicts.
