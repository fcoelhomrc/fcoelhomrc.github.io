I built a test set of 100 questions over 100 machine learning papers, and every question points at the exact chunks it was written from. That turns retrieval scoring into arithmetic on integer ids: free, deterministic, and runnable on every change. Parts 2 and 3 build on it.

This post covers the corpus, the question generation with [Ragas](https://docs.ragas.io), the five things that broke when I ran it, and what curation removed. Everything here is in [papers-please](https://github.com/fcoelhomrc/papers-please), checked against commit `361ff06` (12 Sep 2026).

## The system under test

Papers, Please pulls papers from Semantic Scholar, runs OCR on the PDFs with Docling, splits the text into 256-token chunks and indexes them. A search page and a chat agent query the index.

Retrieval combines BM25 over Postgres text with dense vectors from Pinecone." />

## A corpus built to be hard

Retrieval is only hard when wrong answers look like right ones. A hundred papers from twenty unrelated fields would be separated by keyword overlap alone, and every configuration would score close to 1.0.

So the corpus is five topics of 20 papers each, chosen to share vocabulary: retrieval and RAG, agents and tool use, LLM evaluation, efficient inference and quantization, and alignment. I staged 213 candidates from Semantic Scholar and kept 100 by hand, including near-duplicates on purpose (competing methods for the same problem, v1 and v2 of an idea).

Getting the PDFs needed one trick. Semantic Scholar's open-access link usually points at ACL Anthology, MDPI or doi.org, and doi.org returns 403 to a script. In a sample of 1,000 search results, 73 had an arxiv.org link but 187 had an arXiv id. Building `https://arxiv.org/pdf/{id}` from the id and keeping only arXiv papers gave 100 of 100 downloads ([#41](https://github.com/fcoelhomrc/papers-please/issues/41)).

The final corpus is 11,381 chunks, about 114 per question. On the first ingest, papers ranged from 28 to 833 chunks ([#43](https://github.com/fcoelhomrc/papers-please/issues/43)).

## Generating questions with Ragas

Ragas builds a knowledge graph over your documents, then writes questions by walking it. An LLM extracts a summary, themes and named entities from each node. Edges connect nodes with similar summaries or shared entities. Three synthesizers then pick a node or a cluster and write a question with a gold answer.

<Diagram src="blog/rag-eval/testset.svg" alt="Corpus to seed pool to a per-topic knowledge graph, then three Ragas synthesizers produce 155 questions, mapped to chunk ids by exact text lookup, reviewed and cut to 100." caption="Seed chunks are sampled per topic; the whole corpus stays in the index as the haystack." />

Two settings decide whether the questions can be scored without a model.

1. I give Ragas my chunks, one document per chunk, instead of the PDFs. Its default transforms insert a `HeadlineSplitter` when a quarter of the documents exceed 500 tokens, and that re-splits nodes. So I pass the transform list explicitly and no splitter ever runs.
2. Questions come from a seed pool of 80 chunks per topic. The full corpus stays in the index, so every question has thousands of plausible distractors.

Because nothing re-splits the text, every gold passage Ragas hands back is byte-identical to a row in my `chunks` table. A dictionary lookup turns each passage into a chunk id. All 155 generated questions resolved to at least one chunk id; 46% of the kept questions have one gold chunk, 45% have two and 9% have three.

## What broke when I ran it

None of these raised a clear error at the point of failure. Most of them produced a test set that looked fine.

| Problem | What happened | Fix |
|---|---|---|
| Special tokens in the text | LLM papers quote the end-of-text marker, and tiktoken raises on it inside every extractor call | Encode with special tokens allowed as text |
| Similarity threshold 0.5 | 94.7% of the 79,401 chunk pairs got an edge, and cluster search hung for 13 minutes | Pick the threshold per topic to target about 120 edges (0.74 for agents) |
| One failed entity extraction | 1 of 1,197 calls hit its token limit; the relationship builder then raised and produced zero entity edges, so no multi-hop specific questions | Drop incomplete nodes between extraction and relationship building |
| Reasoning ate the output | GLM 5.3 Flash spent all 8,192 output tokens reasoning and returned no answer | Set reasoning effort to low: same JSON, about 4× fewer output tokens |
| Multi-hop prefixes | Multi-hop passages carry a `<1-hop>` prefix, so 8 of 11 missed the exact lookup on a trial | A counter of unmapped passages caught it before the full run |

Ragas also drops a synthesizer silently when the graph has no clusters for it. The generator now checks cluster counts first and stops if a synthesizer would get none ([#44](https://github.com/fcoelhomrc/papers-please/issues/44)).

## Balanced seeds did not give balanced questions

The first set used a seed pool of exactly 80 chunks per topic. Ragas picks seeds by their position in the graph, and the agents papers dominated it.

After curation the first set had 58 agents questions and 8 alignment questions, so the headline number mostly measured one topic. Keep rates were similar across topics (62% to 87%), so the skew came from generation. The fix was to generate each topic separately, 31 questions each, and cut to exactly 20 per topic.

## Curation removed a third

Ragas saves you from writing questions. It does not save you from reading them.

The 155 generated questions went through a review pass: Claude Opus scored each one from 0 to 100 in its own call, with reasons and flags. It dropped 34. A quota of 20 per topic, filled by score, cut 21 more. Every verdict goes through the same review page as a manual decision, so any of them can be overridden by hand.

Two of these are worth knowing before you generate your own set.

- A question that names its own answer ("What MiniLM variant does...") is retrieved by BM25 on the entity alone. Every configuration then scores the same on it, and real differences vanish.
- A multi-hop abstract question often asks about "these approaches" without saying which. No user would ask it.

The review also edited 18 of the kept questions, several to fix factual errors in Ragas' own gold answers. If you edit a question, edit its gold answer too, or every metric that grades against it goes stale.

One finding came from the review prompt itself. The first pass dropped 80% of questions seeded from tables as "OCR artifacts". They were fine: Docling writes a table as `row, column = value` triplets before chunking, and the prompt gave the reviewer no way to tell that format from garbage. A neutral paragraph describing the format moved table-seeded questions from 20% kept to 82%.

## Cost, and what this set cannot tell you

The first generation run cost $0.354 in model calls, $0.28 of it for the knowledge graph. I did not record the cost of the regenerated set. Questions come from GLM 5.3 Flash, answers from Qwen3 30B and grades from DeepSeek V4 Flash, so no model grades its own output.

The limits:

- The questions are synthetic. They test what an LLM thought to ask of a passage, and they reuse its vocabulary. Part 2 shows why that matters for BM25.
- The gold chunks are the passages each question was written from. Another chunk may answer it just as well, so label-based scores undercount and read as a lower bound.
- Curation had one reviewer model and no second human, so there is no agreement figure for it.

Part 2 uses these 100 questions to compare five retrievers, a reranker and five query rewrites, without a single model call.
